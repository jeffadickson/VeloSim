01 / The idea

A simulator has several hard jobs.
We could reuse some of them.

Verilog describes hardware: signals, storage, logic, and the rules for when values change. A simulator must understand those descriptions and then reproduce their behavior. Recognizing the language and executing the design are separate engineering problems.

VeloSim uses Surelog to read and elaborate the source, and UHDM to expose the resulting design in a structured form. Our code translates a supported portion of that design into a smaller intermediate representation, generates C++, and executes it with our four-state runtime.

The acceleration came from starting with a structured hardware design instead of starting with a language parser.

Reused foundations

Language understanding and design access

Surelog supplies preprocessing, parsing, and elaboration. UHDM supplies the design object model, serialization, traversal interfaces, and expression utilities used by the exporter. Their upstream projects describe these responsibilities in the Surelog and UHDM repositories.

VeloSim's responsibility

Choosing and executing a precise subset

VeloSim supplies the structural exporter, IR validation, C++ generation, four-state operations, ordered state updates, host API, VPI runtime, and qualification workflows. A design still needs to pass our supported-construct checks before it can run.

This is an architectural explanation of development progress. We have no controlled measurement of how many development hours reuse saved, and this document makes no simulator performance-speedup claim.

02 / Follow one design

Five stages turn source
into executable behavior.

The newer structural RTL backend follows this path. The project also retains an older flat-process IR/kernel path with a narrower counter frontend; that path should not be confused with the FIFO-capable structural backend shown here.

01 · INPUTActual RTLYour .sv design, top module, include paths, and macro definitions.
02 · FRONTENDSurelogProcesses source and elaborates the chosen design. Writes surelog.uhdm.
03 · HANDOFFUHDMA navigable design: signals, widths, expressions, processes, and assignments.
04 · OUR COMPILERVeloSimChecks the supported subset, exports velosim.rtl.v1, and generates C++.
05 · EXECUTIONNative modelCMake/Ninja builds a trace executable or a reusable C++ model with the VPI runtime.

UHDM is the data handoff in this diagram. Surelog writes it; the VeloSim exporter reads it through the UHDM C++ library. UHDM does not execute the model for us.

  1. Preprocess, parse, elaborate.Preprocessing handles source directives such as includes and macros. Parsing recognizes language structure. Elaboration works out design structure and parameter/type information for the selected top. Surelog's broad frontend capability does not imply equally broad VeloSim execution support.
  2. Inspect objects instead of matching source text.Our C++ exporter walks UHDM handles and uses facilities such as UHDM::ExprEval. For example, it can ask about an expression's type, operands, and width rather than trying to infer a FIFO from a few lines of text.
  3. Lower to a deliberately smaller language.The JSON IR records named signals, memories, continuous assignments, an optional clock, and a statement tree. Unsupported constructs produce errors. That boundary keeps later compiler stages from silently inventing behavior.
  4. Compile the behavior we accepted.C# validates the IR and emits calls to VeloSim's C++ operations. A C++ compiler builds the result. The standalone design executable runs without .NET or Surelog; generating and compiling a new model still requires the appropriate tools.
New: all three additions together

A clockless population counter with a parameter bias

An always_comb block calls an automatic function. The function returns the captured BIAS immediately for zero input; otherwise a bounded loop sums the eight input bits and returns the sum plus that bias. There is no invented clock. For inputs 0, 1, 3, 255 and 128, the generated native SDK and Icarus both returned 3, 4, 5, 11 and 4.

Surelog/UHDM supplied the typed function and declaration scopes. VeloSim supplied path termination, the loop proof, parameter binding and execution. Qualification also exposed malformed upstream parameter links and lossy folding, so VeloSim reconnects only unambiguous original typed declarations and rejects unsupported constant forms. Read the original example, bounded contracts and measured evidence.

Implementation trail: frontend orchestration → structural UHDM exporter → IR validation and C++ generation → four-state operations.

Why adding an operator became a manageable task

Consider a right shift. Surelog/UHDM already gives us a shift expression and its operands. We still have to recognize and validate that operation, preserve width rules, implement X/Z and large-shift behavior, generate the appropriate C++ call, and compare the result against Icarus. Reuse made the task smaller; it did not supply the execution semantics automatically.

Pin the handoff

The qualified toolchain uses matching revisions: Surelog 6db44ea and UHDM 7c42de4. Pinning makes the design representation and APIs reproducible instead of assuming unrelated upstream versions fit together.

Keep an independent answer

Surelog and Icarus receive the same design .sv path in the structural conformance tests. Icarus also receives a generated stimulus testbench. We compare complete output traces, and FIFO tests add a queue oracle to check data ordering and acceptance independently.

04 / Inside the engine

A clock edge is a sequence
of carefully ordered decisions.

Hardware assignments such as q <= q + 1; use nonblocking assignment semantics. Reading the old state and publishing the next state are separate steps. Within the supported single-process subset, VeloSim generates that separation explicitly.

One evaluation, in order

  1. Settle supported continuous assignments using the current inputs and state.
  2. Detect an evaluated, known 0 → 1 clock transition.
  3. Read the pre-edge state and compute ordered nonblocking updates into next-state storage.
  4. Commit the next state, then settle continuous assignments again.
  5. Dispatch value-change observations and the supported read-only callback phase.

Without a rising edge, continuous outputs can still change. Evaluating a high clock twice does not execute the sequential process twice.

Four-state words

Zero, one, unknown, high impedance

The runtime stores a word's known-one bits, X mask, Z mask, and width. This lets it preserve uncertainty rather than silently turning unknown values into zero.

value

known ones1 0 0 0

Z mask0 0 0 1

Operations have their own rules: 0 & X = 0, while 1 & X = X. This digital Z representation does not add electrical strength resolution or resolved-net support.

05 / Connecting other code

Two ways to drive
the same model state.

C++ host

Public ports and explicit evaluation

The exported V<top>.h class lets an application drive inputs and call eval(). timeInc() advances checked host time; final() dispatches supported end callbacks once. Use bits() to preserve X/Z.

Vexternal_counter top;
top.rst_n = 0;
top.enable = 1;
top.data = 42;
top.clk = 0; top.eval();
top.clk = 1; top.eval(); // synchronous reset

top.rst_n = 1;
top.clk = 0; top.eval();
top.timeInc(1);
top.clk = 1; top.eval(); // count and sample
auto bits = top.sampled.bits();
top.final();

The host pattern is influenced by Verilator's documented model interface. VeloSim has its own port proxies and runtime, without Verilator binary compatibility or a DPI layer.

Native C plugin / VPI subset

Find signals and observe changes

A plugin can look up named signals, inspect metadata, read four-state values, deposit immediate input values, and register supported callbacks. It exports a startup table and is loaded before the first evaluation.

vpiHandle q = vpi_handle_by_name(
    "external_counter.q", NULL);

s_vpi_value value = {0};
value.format = vpiHexStrVal;
vpi_get_value(q, &value);

// The real example also registers
// value-change and read-only callbacks.

Both interfaces reach the same state. A C++ drive can therefore trigger a VPI value-change callback after evaluation. Supported read-only callbacks observe the settled result; callback input deposits are deferred according to the documented phase rules.

The example plugin is compiled against Icarus's independent VPI header during qualification. That checks the tested API boundary, not compatibility with every VPI client.

The subtle point: VPI appears in two different places.

At compile time: traverse UHDM

Our exporter uses UHDM's VPI-style access to inspect the elaborated design. Those handles refer to design-description objects: expressions, declarations, processes.

At run time: access VeloSim

Our own shared library implements a bounded VPI C interface for signal state and callbacks in the running model. It has its own header and ABI checks. We did not turn UHDM's traversal library into a simulator by loading it.

An API standard can be used at both boundaries while the objects and responsibilities behind it remain different.

The reusable SDK contains the generated model header, IR snapshot, runtime source and headers, CMake file, README, and a hash manifest. Its relative manifest paths and Linux origin-relative library path support relocation. Creating a new SDK requires the compiler workflow; using an already-built host does not require the frontend.

Supported structural path

Real, bounded RTL behavior

  • One known-clock posedge always_ff process with ordered nonblocking updates.
  • Unsigned four-state words from 1 to 64 bits, canonical packed ranges, and bounded one-dimensional word memories.
  • Supported arithmetic, logic, comparisons, shifts, reductions, conditional expressions, packed reads, concatenation, and constant replication.
  • Supported if/exact-case control and acyclic continuous logic, including the documented FIFO examples.
  • Reusable C++ hosts and a tested VPI subset accessing the same state.
Remaining language work

The frontend can understand more than we run

General multi-process scheduling, arbitrary hierarchy, generate scopes, signed operations, general functions/tasks, arbitrary timing, asynchronous reset, resolved nets, and broad SystemVerilog testbench semantics remain outside this backend's supported subset.

VPI support also remains bounded: no general delayed/force/release puts, system-task registration, VPI memory-element access, or full event-region scheduler. Full cocotb compatibility has not been established.

The single-process structural model executes serially. Worker settings and parallel build jobs are recorded, but they do not demonstrate parallel simulation speedup.

How do we know we are parsing the same input files?

Structural conformance reports record the exact source path supplied to Surelog and Icarus, plus hashes for source, tools, build inputs, artifacts, and traces. The reference testbench adds stimulus around that design. Tests also assert expected interfaces before generating comparisons, reducing the chance that both checks silently omit a signal.

Could two simulators agree on the same wrong FIFO?

Yes. Differential agreement checks agreement with another implementation, but it does not prove the design matches its intended contract. FIFO tests also use an independent queue oracle for acceptance, flags, and data ordering. A wrong-read-pointer mutation was detected by that oracle even when both simulators agreed on the altered RTL.

Does high code coverage mean we nearly support all Verilog?

No. Coverage describes which lines and branches in the measured implementation were exercised. Language support is a separate inventory of accepted syntax and correct semantics. A small compiler can have excellent coverage while intentionally rejecting large parts of the language.

What would expand the simulator next?

The largest architectural step is a well-specified scheduler for interacting processes and event regions, accompanied by independent conformance tests. Broader signed sizing, hierarchy/elaboration lowering, reset forms, memory interfaces, and plugin compatibility need their own implementation and evidence. Reusing the frontend keeps those efforts focused on execution rather than reparsing the language.
