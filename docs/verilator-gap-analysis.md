# VeloSim / Verilator gap analysis

Audit date: 2026-10-26. Repository: jeffadickson/VeloSim, branch `procedural-types-arrays`, HEAD `fa7cd2fbd962dde1f95ffb29e6b3e46a01a5cae1` **plus uncommitted associative-array/frontend work**. This report supersedes historical README/roadmap capability summaries for planning; it does not rewrite their historical qualification results.

Live tracking: [GitHub epic #1](https://github.com/jeffadickson/VeloSim/issues/1) with 20 open work-package issues. Local plans have not been pushed.

## Decision

Library follow-up: [19 evaluated reuse opportunities](library-opportunities.md) cover both existing code and remaining features, with recommendations, tradeoffs and acceptance checks added to all 20 existing package issues. The [structured index](library-opportunities.json) distinguishes installed/existing facilities from candidates; no new dependency or implementation result is implied.

VeloSim is a bounded, compiled four-state RTL simulator with useful working vertical slices. It is not yet a drop-in Verilator replacement. A new bounded explicit-time SDK slice now executes resumable processes; the critical path is completing its broader timing, interacting-process, call and elaboration acceptance. Broader language, testbench and ecosystem work follows. Keep leveraging Surelog/UHDM, standard C++ containers and existing .NET tooling; replacing the implementation language does not close these semantic gaps.

There are **60 audited capability areas and 20 work packages**. These are planning units, not a percentage of IEEE SystemVerilog conformance. A feature family may contain many independent semantics. “Missing” describes the inspected VeloSim execution path, not what Surelog can parse.

## Baselines and evidence rules

- **Executed reference:** Verilator 5.020 2024-01-01 rev (Debian 5.020-1). All new probes below used this installed executable, not 5.052.
- **Documented comparison target:** official Verilator 5.052 documentation and [release tag](https://github.com/verilator/verilator/releases/tag/v5.052), checked during this audit. This is a capability target, not an executed compatibility certification. Version the reference environment in WP-01.
- **Source inspection:** native UHDM lowering, normalized C# IR validation/code generation, runtime/SDK/VPI headers, tests and StrictDoc. A frontend accepts only what the lowering and runtime can execute; parser support is insufficient.
- **Historical evidence:** 14/14 focused managed associative tests and 1/1 native test from the immediately preceding work. Adapter-file coverage34/35 lines and59/68 branch outcomes; whole Core focused coverage16.08%/12.16%. Those results are historical to this audit, not a fresh full regression. Native frontend/runtime coverage and broader qualification remain incomplete.
- **Current probes:** 14 original HDL files, each passed unchanged to both Surelog and Verilator. Surelog accepted14; Verilator lint accepted14; VeloSim lowered2 and rejected12. One accepted case silently loses an assertion. These are frontend/lint outcomes, not behavioral simulation passes. Warnings were permitted with `-Wno-fatal`; no warning-free claim.
- **Source provenance:** the exporter was built in the prior successful `binding-build04.log` run. Its audited main/header sources match the worktree after CRLF normalization; raw hashes of both trees and executable are retained in [probe evidence](verilator-gap-probes.json). The audit did not perform a new exporter rebuild or prove a reproducible binary build.
- **No benchmark:** no new speed, memory, parallel scaling, mutation score or full-suite coverage claim. No CI dispatch, code push, or new runtime implementation is part of this analysis task.

Statuses: **partial** means implemented under narrower restrictions; **worktree-focused** means implemented and focused-tested but not broadly qualified/committed; **missing** means absent or explicitly rejected in the inspected path; **not-established** means evidence is insufficient for a support claim; **silent-omission/risk** means successful lowering can hide unsupported executable behavior.

## Reference limitations and intentional differences

Verilator's normal mode is largely two-state; the 5.052 options document `--fourstate` as experimental developer functionality. Preserve VeloSim's bounded X/Z behavior and use independent four-state expectations or Icarus where appropriate. Do not change correct four-state results to match a two-state reference. [Language behavior](https://verilator.org/guide/latest/languages.html#unknown-states), [experimental option](https://verilator.org/guide/latest/exe_verilator.html#cmdoption-fourstate).

The installed5.020 associative comparisons previously exposed signed-negative-key ordering and missing-read insertion differences. The focused comparison uses nonnegative signed keys and guarded missing reads; negative numeric order, missing reads and traversal from absent indices are independently native-tested. These exclusions are not verified reference agreement. Recheck them on the pinned newer reference before declaring current-version Verilator defects.

Full specify/SDF timing checks, strengths/transistor/analog behavior, encrypted IEEE1735 IP, and universal UVM or full-standard compatibility are not justified parity goals merely because Verilator parses related syntax. Verilator documents ignored/restricted forms. Track such cases as separate product decisions, and preserve differences in reference scheduling, array bounds and VPI visibility rather than equating any one implementation with the standard. [Documented limitations](https://verilator.org/guide/latest/languages.html).
